# Общий backend распознавания вин

Независимый Python-пакет: он не импортирует другие модули, а вызывает их по HTTP.
Сначала независимый `wine_label_preprocessing` вызывается по HTTP. Он применяет
EXIF-ориентацию, ограничивает visual-ветку длинной стороной 1600 и OCR-ветку 1920,
не увеличивая маленькие фото. Для DINO/SuperPoint фотометрия выключена; для OCR
включены мягкие brightness ±10% и CLAHE 1.5, unsharp выключен (опционален).
Без внешнего bbox/маски автоматическая локализация и цилиндрическая развёртка
не заявляются: metadata явно указывает `label_bbox_missing`.

DINOv2 giant (1536) получает 20 разных вин; SuperPoint/LightGlue перепроверяет
их и backend оставляет Top-10. Одновременно OCR + multilingual-e5-base (768)
получают свой Top-10. Результаты сводятся по `slug`, а не по ID исходных строк CSV.
OCR может добавить до 10 пропущенных DINO кандидатов с опубликованными эталонами.
Они проходят дополнительный вызов SuperPoint, затем сохраняется общий visual
Top-10. Каждый вызов verifier остаётся в пределах 20 IDs. Это расширение исходной
схемы предотвращает потерю правильного вина на стадии DINO shortlist.

## Два бизнес-эндпоинта

`POST /v1/eval/predict`, multipart-поле **image** — синхронный ответ организатору:

```json
{"slug":"kokur-suhoe-2025"}
```

По умолчанию запрос ждёт завершения всей задачи. Заголовок `X-Job-ID` позволяет
посмотреть полный результат. С асинхронным режимом `?wait=false` ответ HTTP 202:

```json
{"job_id":"...","state":"queued","poll_after_ms":1000}
```

`GET /image/status?job_id=...` возвращает `queued | processing | done | failed`,
этап, прогресс и подробный `result`: кандидаты, ссылки на карточки, оценки веток,
`fusion_mode`, `warnings`, `branch_counts`. Неизвестная/истёкшая задача — HTTP 404.
`history` сохраняет этапы с `elapsed_ms`, включая preprocess, начало/конец DINO,
OCR, SuperPoint, OCR-rescue, fusion, color, vintage и done/failed. Текущий stage
не описывает обе параллельные ветки сразу; история доступна и после завершения.
Прогресс монотонный, не прогноз времени. `result.preprocessing` содержит
размеры, параметры, операции и тайминги предобработки без самих изображений.

Файл ограничен 10 MiB, весь multipart — этим объёмом плюс 64 KiB.
Поддерживаются JPEG/PNG/WebP, не более 25 млн пикселей. Пустые/битые файлы
отклоняются до запуска моделей. Содержимое файла важнее присланного MIME.

## Ранжирование и ошибки

Веса адаптивные: при содержательном OCR-тексте `score = 0.3 * visual + 0.7 * ocr`,
при недостаточном тексте — `0.7 * visual + 0.3 * ocr`. Содержательный текст:
не менее 3 разных слов, из них не менее 2 (суммарно 12 букв) помимо общих
винных терминов и названий производителей shortlist, и средняя confidence
распознавания буквенных блоков >=0.75. Числа/ценники не учитываются. Это начальная
эвристика для последующей проверки на размеченных фото команды. Косинус E5 не
используется как confidence OCR. `text_quality`, `ocr_evidence`, `fusion_weights`
и `pipeline_version` в status показывают причину и применённые веса.

При хорошем тексте (`text_primary`) объединяются OCR/visual-кандидаты;
отсутствие в visual Top-10 само по себе не исключает текстовое совпадение.
При отсутствии геометрии (`text_primary_dino`) visual-сигнал берётся из DINO.
При слабом тексте (`weighted_visual`) OCR только переставляет кандидатов с
ненулевым SuperPoint; нет жёсткого отсечения по пересечению Top-10.
После него слабый цветовой сигнал: `0.95 * score + 0.05 * palette_similarity`
(`COLOR_WEIGHT`, можно 0). Сравнивается палитра центральной/нижней области фото
с эталоном, не тип вина по цвету этикетки. Это экспериментальный proxy, не сегментация.
Один уверенно прочитанный год (OCR confidence >=0.8, без founding/since) ставит
кандидатов с совпавшим явным годом выше неизвестных/несовпавших годов в shortlist.
При нескольких годах фильтрации нет. Год не выводится из истории винодельни.
Текущий CSV не содержит отдельной колонки года; название+slug дают явный год
для 116 из 2103 slug. Неизвестные годы не выдумываются, глобального отсечения нет.
При равенстве сохраняется порядок DINO. Сигналы не калиброваны; это **не
вероятность** правильного ответа и не организаторский confidence.

Чтобы pipeline мог отвечать при непрочитанной этикетке, явно предусмотрены:

- `visual_fallback`: нет текстовых совпадений среди визуальных кандидатов —
  лучшие геометрически подтверждённые кандидаты, `0.7 * visual`;
- `dino_fallback`: все геометрические оценки нулевые либо verifier недоступен —
  исходный DINO Top-20;
- отсутствие DINO/эталонов — failed/HTTP 503, без выдуманного slug.

Недоступность OCR/verifier отмечается в `warnings`. Таким образом, HTTP 200
от eval endpoint сам по себе **не доказывает**, что все модели успешно отработали:
проверяйте полный статус. При слабом тексте OCR-кандидаты без геометрической
поддержки не становятся fallback; `dino_fallback` берёт исходные DINO-кандидаты.
У OCR-rescue нет придуманного DINO cosine: `dino_score=null`.
Эти правила нужно оценить на размеченной валидации команды.

### Лучший вариант с предупреждением о неуверенности

`decision` содержит accepted/reason/score/margin, отдельные оценки ветвей,
пороги и `calibrated=false`. Начальные пороги: MATCH_MIN_SCORE=0.60,
MATCH_MIN_MARGIN=0.03, MATCH_MIN_GEOMETRY=0.65. Нужна визуальная поддержка,
а не один высокий E5 score. Почти равные кандидаты, слабая поддержка или
явное несовпадение года дают `decision.accepted=false`. Это только предупреждение:
успешное распознавание с кандидатами всегда возвращает `status=ok`, Top-1 slug
и карточку. Frontend показывает «Оценка совпадения: X%» — округлённый ранговый
score, умноженный на 100 (с ограничением 0–100), с явной пометкой, что это не
вероятность правильного ответа. При accepted=false дополнительно показано
«Неуверенное совпадение». Пороги не блокируют карточку и не изменяют ранжирование.
При неуверенности frontend показывает до 10 разных кандидатов из `candidates`
в итоговом порядке: основную карточку и до 9 дополнительных со ссылками и score.
Они не являются рекомендациями и не меняют Top-1; синхронный eval-контракт остаётся
`{"slug":"..."}`. Если кандидатов меньше, список не дополняется вымышленными винами.
Это эвристика, не доказательство отсутствия вина в каталоге и не вероятность.
Для калибровки пока недостаточно размеченных примеров. По добровольным отзывам
можно позднее подобрать пороги, учитывая ошибочные ответы и отказы отдельно.

Почти точное совпадение DINO >=0.985 и SuperPoint >=0.95 с единственным
подтверждённым пользовательским эталоном имеет приоритет над семантическим
OCR. Это позволяет новой подтверждённой фотографии исправить прежнюю ошибку,
даже когда E5 по-прежнему предпочитает описание другого вина.
Организаторский синхронный endpoint продолжает возвращать Top-1 slug согласно
его контракту; подробный статус сохраняет диагностику и предупреждение.

## Обратная связь и набор для улучшения поиска

`POST /feedback` принимает JSON `{"job_id":"...","is_correct":false,"correct_slug":null}`.
Правильный ответ можно указать slug или HTTPS-ссылкой на карточку vino-svoe.ru;
он проверяется по `wines`. Для «Угадал» правильным slug становится предикт.
Для «Не угадал» пользователь заполняет любые известные сведения:
`wine_information={name,year,locality,winery,notes}`. Они отправляются в
OCR-сервис `POST /match/text`: E5 строит query embedding и ищет по существующим
текстовым векторам каталога. Пороги TEXT_LABEL_MIN_SCORE=0.90 и
TEXT_LABEL_MIN_MARGIN=0.015 относятся к rescaled cosine, не к вероятности.
Недостаточный текст, низкое сходство, маленький отрыв, конфликт года или
несовпадение с отрицательной оценкой дают `saved=false`: новый отзыв и фото
не записываются. Клиент получает просьбу уточнить сведения. Ранее сохранённые
данные такой отказ не удаляет. Для внутренней отладки ссылка на карточку
поддерживается и в свободном поле, но это не рекламируется в пользовательском UI.

Снимок и исходный результат берутся с сервера. Задача должна завершиться;
для первого отзыва она хранится до часа/вытеснения из 16 мест. Уже сохранённый
отзыв можно уточнять после рестарта, используя контекст из PostgreSQL.
Повторная оценка обновляет запись и не увеличивает счётчик. При смене slug
прежний пользовательский эталон отзывается, если его не использует другой отзыв.

Backend при запуске создаёт две добавочные таблицы: `recognition_samples`
(SHA-256 и оригинальные байты фото, дедупликация по хешу) и `recognition_feedback`
(предикт, оценка пользователя, исправление, полный результат с версией/весами,
время, пользовательские сведения и диагностика текстового выбора).
После прямого подтверждения «Угадал», точного идентификатора или достаточно
однозначного E5-сопоставления ставится очередь `embedding_state=queued`.
Один фоновый worker применяет ту же предобработку, вызывает уже загруженный
GPU DINO `/embed` и добавляет giant/1536 в `reference_images` для MIN(wines.id)
данного slug. Фото лежит в `data/reference/feedback/<id>/<sha256>.png`.
DINO и SuperPoint видят новый эталон без рестарта; исходные каталожные эталоны
сохраняются. Состояния: queued/indexing/ready/failed/unlabeled; ошибки можно
повторить сохранением отзыва. Очередь восстанавливается при рестарте.
`ready` устанавливает review_status=approved по подтверждению пользователя.
Противоречивые разметки одного снимка разными отзывами блокируют публикацию.
Сохранение атомарно и переживает рестарт.
Исходное фото сохраняется только при отзыве, а не при каждом запросе; фотографии
в этих таблицах хранятся до ручного удаления. В памяти остаётся не более 16
исходных фото до 10 MiB каждое плюс рабочие буферы.

`GET /feedback/status?job_id=...` показывает состояние добавления эталона.
`GET /feedback/stats` возвращает total/correct/incorrect/labeled/pending_review
и indexed/indexing/index_failed.
Это статистика добровольных отзывов, а не точность на организаторском eval.
Проверенную разметку можно экспортировать для следующего дополнения индекса:

```bash
DATABASE_URL=... python -m wine_pipeline.feedback_export --output ./feedback-review
# После проверки конкретных записей установите review_status='approved'.
DATABASE_URL=... python -m wine_pipeline.feedback_export --output ./feedback-approved --approved-only
```

Экспорт создаёт фото и `feedback.jsonl` с хешем, slug и статусом проверки;
существующий manifest не перезаписывает. Экспорт — дополнительная возможность
аудита и анализа уже пополняемого индекса. Организаторский eval в этот набор
не включайте. Backend имеет RW-доступ только к feedback-папке; DINO и
SuperPoint читают общий DATA_ROOT. Для Compose заранее создайте
`modules/dinov2_retrieval/data/reference/feedback` с правом записи для UID 1000.

## Каталог: подготовка без повторной генерации

В `wines` уже есть эмбеддинги, однако DINO и SuperPoint читают `reference_images`.
Публикация переносит существующие giant-векторы, не запускает модели:

```bash
cd modules/dinov2_retrieval
docker compose --profile pipeline run --rm --entrypoint python wine-pipeline \
  -m dinov2_retrieval.wine_catalog.publish_references --data-root /data
```

Канонический `wine_id = MIN(wines.id)` для каждого `slug`.
Каталог сохраняет исходные строки, text embedding и их ID; backend разрешает
OCR-ID обратно в slug. OCR SQL ищет десять **разных slug**, чтобы дубликаты CSV
не занимали места в Top-10.

Публикация проверяет размеры векторов и существование файлов, создаёт hard links
(при невозможности — копии) в `data/reference/catalog/<id>`. Это нужно, потому
что один исходный файл может относиться к разным винам, а image_uri в индексе
уникален. Повторный запуск идемпотентен, не удаляет старые эталоны. Для полного
замещения старого каталога нужна отдельная согласованная процедура очистки.
Пути в БД публикуются относительно выбранного контейнерного корня: используйте
одинаковый `/data` в издателе и ML-сервисах.

## Запуск Docker / GPU

Из корня репозитория. Предполагаются уже импортированная БД, локальные данные,
кэш весов и доступный NVIDIA GPU в Docker:

```bash
docker compose -f modules/dinov2_retrieval/docker-compose.yml up -d postgres
docker compose -f compose.pipeline.yml up -d --build
```

Backend доступен на `http://127.0.0.1:8080/docs`. ML-сервисы не публикуют порты
на хост. БД — существующая `dinov2_retrieval_default`; новый пустой каталог
не создаётся вместо текущего. Пароль dinov2 — только локальный dev-default,
для сервера задайте DATABASE_URL с секретом через окружение.

Локальная конфигурация для RTX 2050 / 4 GiB:
DINO giant CUDA/float16, SuperPoint CUDA, PaddleOCR и E5 CPU.
Для CPU OCR `OCR_USE_DOC_UNWARPING=false`, `OCR_TEXT_DET_LIMIT_TYPE=max`,
`OCR_TEXT_DET_LIMIT_SIDE_LEN=960`. Без max большой вход 3000×4000 мог завершить
OCR по OOM. Детектор сам возвращает координаты в своей входной системе.
Документация параметров: [PaddleOCR](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html).
Предобработка CPU/OpenCV не требует GPU и не загружает нейросетевые веса.
У DINO запрос и каталог используют одинаковую точность/предобработку.
Явное `cuda` не позволяет незаметно переключиться на CPU.
RAM всё равно нужна для HTTP, изображений, PostgreSQL, CPU-ветки и загрузки весов.

Продовый all-GPU режим — только после измерения суммарной VRAM:

```bash
docker compose -f compose.pipeline.yml -f compose.pipeline.gpu.yml build ocr-cuda-base
docker compose -f compose.pipeline.yml -f compose.pipeline.gpu.yml up -d --build
```

В нём Torch CUDA 12.6 / 2.8.0, PaddlePaddle GPU 3.2.2, `OCR_DEVICE=gpu:0`,
`TEXT_EMBEDDING_DEVICE=cuda`. CPU Paddle удаляется перед установкой GPU-варианта.
Это отдельный профиль развёртывания, не обещание, что все модели вместятся в 4 GiB.
См. [GPU в Docker Compose](https://docs.docker.com/compose/how-tos/gpu-support/)
и [установку PaddlePaddle](https://www.paddlepaddle.org.cn/documentation/docs/en/install/index_en.html).
Быстрый контроль:

```bash
docker compose -f compose.pipeline.yml exec dinov2 python -c \
  "import torch; print(torch.cuda.is_available(), torch.cuda.get_device_name(0))"
docker compose -f compose.pipeline.yml exec superpoint python -c \
  "import urllib.request; print(urllib.request.urlopen('http://localhost:8000/health').read())"
nvidia-smi
```

Первый OCR-запрос скачивает модели Paddle и загружает E5; `/health` OCR — только
liveness. Перед измерением latency прогрейте OCR реальным фото команды.
Кэши Paddle/E5/LightGlue сохраняются между запусками.

## Проверка API без организаторского eval

```bash
curl -i -F 'image=@/path/to/team-validation.jpg' \
  http://127.0.0.1:8080/v1/eval/predict

curl -F 'image=@/path/to/team-validation.jpg' \
  'http://127.0.0.1:8080/v1/eval/predict?wait=false'
curl 'http://127.0.0.1:8080/image/status?job_id=ID_FROM_RESPONSE'
```

Организаторский `participant_test.sh` / `queries.tsv` запускаются **в финальной
фазе**, после проверки всех веток. Контрольные фото организатора не используются как
валидация для настройки весов. Скрипт ожидает синхронный режим: не добавляйте
`wait=false`. Существующий predictions.jsonl сначала переименуйте.

По уточнению организаторского требования обе копии `participant_test.sh`
используют `curl --max-time 120` (120 секунд на запрос). Ранее в предоставленном
файле стояло 10 секунд; прогрев не отменял этот лимит.
Прогон распакованного `Датасет/eval` от 2026-09-29 (3 изображения) на текущей
RTX 2050 дал 3 timeout и `predicted_slug=null`; это не accuracy=0%, так как
ответ не успел попасть в файл. Выход сохранён отдельно:
`reports/predictions-organizer-20260929.jsonl`. В том первом прогоне таймаут не изменялся;
контрольные изображения не использовались для подбора параметров.
Этот первый отчёт не подтверждает прохождение актуального 120-секундного лимита.
Повторный запуск сохраняется в `reports/predictions-organizer-120s-20260929.jsonl`;
исходный отчёт не перезаписывается. Изменился только таймаут, не модели или веса.
Повторный прогон с лимитом 120 s завершился: 3/3 непустых slug без timeout.
Latency: 21.954, 22.763 и 22.643 s. Это прохождение протокола и лимита времени,
не оценка точности: правильные ответы остаются у организатора.

На фото команды `91.07_20-08-2026_18-37-46.webp` полный новый pipeline вернул
`aratti-kaberne-sovinon-2021-krasnoe-suhoe`, OCR-год 2021, без warnings.
Отчёт `reports/aratti-preprocessing-20260929.json`: около 27.1 s, preprocessing
~1.7 s включая decode/кодирование/HTTP, DINO ~1.5 s, OCR ~8.8 s,
SuperPoint основной ~17.2 s, OCR-rescue ~6.3 s. OCR идёт параллельно с visual.
Это один размеченный пример, не оценка общей точности. Следующий performance
шаг — повторное использование признаков запроса/эталонов в verifier и измерение
на валидации команды, не подбор весов по организаторским query.

## Ограничения / дальнейшее продовое усиление

Очередь ограничена 16 задачами, одна задача распознаётся за раз; две её ветки
работают параллельно. Результаты хранятся в памяти до часа и раньше вытесняются
при заполнении лимита; перезапуск их теряет. Используйте **один uvicorn worker**.
Для multi-worker/нескольких реплик нужны Redis/БД для задач и внешняя очередь.
Прогресс относится к этапам, а не является оценкой оставшегося времени.
Timeout каждой HTTP-ветки по умолчанию 180 s (`BRANCH_TIMEOUT_SECONDS`).
В production также нужны аутентификация, TLS и ограничение запросов на ingress.

```bash
.venv/bin/pip install -e '.[dev]'
.venv/bin/python -m pytest -q
```

Тесты не используют сеть, PostgreSQL, GPU или веса. Они проверяют JSON-контракт,
polling, очередь, ошибки, ограничение multipart, порядок/веса fusion,
параллельное начало веток и HTTP-адаптеры. Проверка self-match эталона подтверждает
связность pipeline, **не** качество распознавания новых фотографий.

Воспроизводимый end-to-end smoke-test (уже требует запущенные реальные сервисы):

```bash
.venv/bin/python -m wine_pipeline.smoke \
  --image /path/to/team-validation.webp --expected-slug EXPECTED_SLUG \
  --output reports/smoke.json
```

Он проверяет sync-ответ и async polling, требует непустые результаты всех
трёх веток и отсутствие warnings. JSON-отчёт сохраняется отдельно от датасета.
